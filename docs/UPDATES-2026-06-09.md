## 1. Лже-инсайдеры (главная причина убыточных сигналов)

**Проблема.** В БД из 10 «китов» 6 имели отрицательный PnL. Кошелёк `0x06dc…`
с PnL **−$126,910** и 355 сделками был помечен «🥷 INSIDER, age 1д» и весь день
генерировал сигналы, которые бот копировал.

**Причины:**
- `get_first_trade_ts()` (src/api.py) пагинирует максимум 2000 последних сделок.
  У гиперактивного бота все 2000 укладываются в сутки → min(timestamp) давал
  «возраст 1 день» → ложный флаг инсайдера. Ловушка в CLAUDE.md была описана
  наоборот («старый кошелёк точно не молодой» — на деле именно старые активные
  кошельки ложно становились «молодыми»).
- `qualifies()` (src/scout.py): инсайдеру хватало WinRate ≥ 25% — требования
  к PnL не было вообще, убыточные кошельки проходили фильтр.

**Исправление:**
- `get_first_trade_ts()` возвращает `None` («возраст неизвестен»), если история
  глубже лимита пагинации. Точный возраст — только при исчерпанной истории.
- Инсайдер обязан иметь WinRate ≥ 50% (`insider_min_winrate`: 0.25 → 0.50)
  **и** PnL > 0 (новый параметр `insider_min_pnl`).
- `db.remove_unqualified_whales()` зеркалит те же правила (добавлен параметр
  `insider_min_pnl`).

## 2. Конфискация выигрышей при разрешении рынка (src/tracker.py)

**Проблема.** Когда рынок разрешался, CLOB `/price` отдавал 404, и
`manage_positions` закрывал позицию «по цене входа, PnL = 0». Выигрыши
фиксировались как ноль, проигрыши — как убытки через SL. Машина отрицательного
матожидания даже при хорошем сигнале.

**Исправление:**
- При 404 исход берётся из `api.get_market_resolution()` (функция существовала,
  но нигде не вызывалась) → закрытие по **1.0 (WIN) / 0.0 (LOSS)**.
- Если исход ещё неизвестен — ждём grace-период (`resolution_grace_hours`=24)
  после `close_at`, и только потом закрываем нейтрально по входу.
- Позиции теперь хранят `cond_id` и купленный `outcome` (нужны для определения
  исхода). `resolve_token_id()` возвращает пару `(token_id, outcome)`.
- LIVE-режим: разрешённый токен нельзя продать через CLOB (нужен redeem через
  CTF) — позиция снимается с трекинга с предупреждением «redeem вручную»
  (`_settle_resolved()`).

## 3. Вход по устаревшей цене + скрытый баг SELL-сигналов (src/tracker.py)

**Проблема 1.** `execute_trade` входил по `median_price` сделок кита из окна
до 12 часов давности, paper-филл исполнялся по этой цене безусловно —
статистика была нерепрезентативна.

**Проблема 2 (найдена попутно).** При SELL-сигнале бот покупал
*противоположный* токен, но по цене *исходного*: кит продал YES по 0.9 →
paper-покупка NO по 0.9 при реальной цене NO ≈ 0.1 — мгновенный −89% в учёте.

**Исправление:**
- Вход по **текущему ask** из стакана: `api.get_price(token_id, side="buy")`.
- Контроль слиппеджа: если ask убежал от референсной цены кита больше чем на
  `max_entry_slippage` (5 центов) — пропуск «поезд ушёл». Для SELL-сигналов
  референс = 1 − цена кита (цена противоположного токена).
- Попутно: кэш цен в `api.get_price` теперь ключуется `(token_id, side)` —
  раньше bid и ask смешивались в одной записи.

## 6. Один путь запуска (run.sh / update_daily.sh)

**Проблема.** `run.sh` запускал трекер без pid-файла, `update_daily.sh` — со
своим. Это позволяло двум трекерам работать параллельно: сегодняшние сигналы

**Исправление.** `run.sh` — единственный путь запуска: kill по pid-файлу +
`pkill` процессов-сирот + запись нового pid. `update_daily.sh` вызывает `./run.sh`.

## 2. Петля обратной связи: таблица `signal_outcomes` (src/db.py, src/tracker.py)

Каждый сигнал фиксируется в БД **независимо от того, открыли ли мы позицию** —
оцениваем кита, а не своё исполнение:

```sql
signal_outcomes (id, cond_id, market_title, side, outcome, entry_price,
                 signal_type, wallets, created_at, resolved_at, winner, won)
```

- `tracker.check_signal_outcomes()` каждые 30 минут (`outcome_check_interval`)
  сверяет нерешённые сигналы с `api.get_market_resolution()`:
  BUY → кит прав, если его исход выиграл; SELL → если проиграл.
- `db.whale_signal_stats()` — атрибуция по китам: сколько разрешённых
  сигналов, сколько верных.
- `db.prune_bad_performers()` — **авточистка**: кит с ≥ 5 разрешёнными
  сигналами (`prune_min_signals`) и долей правоты < 40% (`prune_min_winshare`)
  удаляется из БД с уведомлением в Telegram. История в `signal_outcomes`
  сохраняется. После чистки списки китов перечитываются немедленно.

Скоринг китов стал самообучающимся: кит оценивается по тому, что его сигналы
реально принесли, а не по снапшоту портфеля.

## 3. Элита: одиночный сигнал — только от проверенных (src/engine.py)

Раньше любой отслеживаемый кит с одной сделкой ≥ порога давал сигнал —
консенсус был мёртвым кодом. Теперь:

- `evaluate_market(..., trusted, elite)`: одиночный режим — только для
  адресов из `elite`; остальные отслеживаемые дают сигнал **только
  консенсусом** (2+ кошелька, перевес 2×).
- Элита (`db.get_elite_addresses`): WinRate ≥ 70% и PnL ≥ $10k
  (`elite_min_winrate` / `elite_min_pnl`), ИЛИ инсайдер, ИЛИ
  lifetime PnL ≥ $25k с leaderboard.
- Без параметра `elite` элитой считается весь `trusted` (обратная
  совместимость, тесты не ломаются).

# Фаза 3 — управление капиталом (реализована 2026-06-09 поздно вечером)

## 1. Sizing по fractional Kelly (src/tracker.py → `position_size_usd`)

Размер позиции зависит от качества кита и цены входа:

```
f* = (p − c) / (1 − c)      p = winrate лучшего кита сигнала (кап 0.95), c = цена входа
size = clamp(банкролл × kelly_fraction × f*,  trade_amount_usd,  банкролл × position_max_pct)
```

- Нет оценённого края (p ≤ c) или нет статистики китов → базовая ставка `trade_amount_usd`.
- `kelly_fraction` = 0.25 (полный Келли слишком агрессивен при шумной оценке p).
- Жёсткий кап `position_max_pct` = 2% банкролла, какой бы ни был «край».

## 2. Лимиты экспозиции (`entry_blocked`)

- `max_open_positions` = 10 одновременных позиций.
- Одна позиция на рынок (по `cond_id`) — никакого усреднения в один исход.

## 3. Дневной стоп-лосс (`daily_stop_active`, data/metrics.json)

Якорь — баланс на начало дня UTC. Просадка ≥ `daily_max_loss_pct` (5%) →
новые входы на паузе до завтра, алерт в Telegram. Управление открытыми
позициями (TP/SL/закрытия) продолжает работать. Файл `data/metrics.json`
(объявлен в конфиге ещё в Фазе 1) теперь реально используется.

## 4. Флиппинг — частичная фиксация (из требований, manage_positions)

Вероятность сместилась на `partial_take_delta` (+5 центов) в нашу сторону →
продаём `partial_take_fraction` (50%) позиции, остаток едет до TP (+10) /
SL (−15) / разрешения рынка. Одна частичная фиксация на позицию
(`partial_done`). Снижает дисперсию и время удержания капитала —
ровно то «динамическое закрытие», о котором говорят требования.
